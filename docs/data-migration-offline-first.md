# Миграция данных и офлайн-режим

## Цели

- Локальная библиотека остаётся доступной без интернета и при недоступности внешних сервисов.
- Обновление приложения не меняет имя пользовательской IndexedDB и не пересоздаёт библиотеку.
- Изменения схемы IndexedDB выполняются последовательными versionchange-миграциями.
- При восстановлении связи пользователь может вручную запустить синхронизацию с MAL, AniList или Shikimori.
- Ни одна внешняя синхронизация не запускается автоматически после reconnect: передача изменений может затронуть удалённый список, конфликты или намерения удаления и должна оставаться осознанным действием.

## Текущая архитектура

### Источник локальных данных

Основная библиотека хранится в IndexedDB с постоянным именем `midahoshi-anime-sync`. В production имя не зависит от query-параметров и не должно меняться между релизами. Не удалять базу, не менять её имя и не подменять локальную библиотеку данными внешнего API.

Локальное создание и редактирование записей сохраняет anime identity и запись с `source: "local"` в IndexedDB. Эти действия не требуют MAL, AniList, Shikimori или работающего API-интеграций. Постеры и внешние каталоги могут быть недоступны офлайн, но это не должно скрывать или удалять локальные записи.

### Миграции схемы

Текущая версия схемы IndexedDB: **v8**.

- v1: базовые хранилища `anime` и `entries`.
- v2: `sourceEntries`, перенос старых записей в source entries.
- v3: `conflictResolutions`.
- v4: `animeRelations`.
- v5: журнал `syncOperations`.
- v6: `syncSessions`.
- v7: `deletionIntents`.
- v8: `appMetadata` с номером схемы. Запись создаётся в той же IndexedDB versionchange-транзакции, что и миграция. Если upgrade-транзакция завершается ошибкой, браузер не должен зафиксировать новую версию базы.

Номер версии приложения в `package.json` и номер схемы IndexedDB решают разные задачи. Версию IndexedDB повышать только при изменении структуры хранилищ или данных, требующем миграции. Обычные UI-релизы не должны пересоздавать базу.

### Автоматическая резервная копия перед миграцией

Перед каждым повышением версии существующей IndexedDB приложение:

1. Открывает текущую базу без запроса новой версии. Если базы ещё нет, проверка не создаёт её и резервная копия не требуется.
2. Считывает все object stores в одной readonly-транзакции, включая `anime`, `entries`, `sourceEntries`, `conflictResolutions`, `animeRelations`, `syncOperations`, `syncSessions`, `deletionIntents` и будущие хранилища, добавленные в старых версиях.
3. Записывает структурно клонированные записи в отдельную IndexedDB с суффиксом `__migration_backups`. Основная база не очищается и не переименовывается.
4. Повторно читает сохранённую копию и проверяет формат, перечень хранилищ и количество записей.
5. Только после успешной записи и проверки разрешает открыть основную базу на новой версии. Если backup не удалось сохранить или проверить, открытие с повышением версии прекращается.

Хранятся последние три автоматические копии для каждой базы. Копия содержит исходную версию схемы и целевые сведения о миграции. Это внутренний аварийный снимок, а не замена экспортируемому файлу: основная и резервная IndexedDB находятся в одном профиле браузера и могут быть удалены при очистке данных сайта или потере профиля. Для важных данных дополнительно сохраняй экспорт на отдельном устройстве.

### Офлайн-поведение

При потере соединения приложение показывает предупреждение, но не блокирует локальную библиотеку и её редактирование. Внешний импорт, синхронизация аккаунтов и обогащение метаданных откладываются до восстановления соединения.

Локальные изменения остаются на устройстве. После reconnect пользователь запускает синхронизацию нужного сервиса вручную. Существующий механизм планирования сравнивает локальные записи с текущим удалённым списком и сохраняет план/журнал операций перед выполнением изменений.

Это не облачная синхронизация и не автоматическая фоновая очередь. До отдельного проектирования нельзя обещать автоматическую отправку в фоне или синхронизацию между устройствами.

## Правила безопасности для следующих миграций

1. Никогда не удалять и не переименовывать production database `midahoshi-anime-sync` ради миграции.
2. Не очищать object stores в upgrade callback, если миграция явно не переносит все записи в новую структуру и не проверяет результат.
3. Все связанные изменения выполнять в одной IndexedDB versionchange-транзакции.
4. Миграция должна быть повторяемой по смыслу и не создавать дубли.
5. Добавлять тесты upgrade с предыдущих поддерживаемых версий, включая заполненные базы.
6. Проверять сохранность anime, aggregate entries, source entries, relations, конфликтов, журнала синхронизации и deletion intents.
7. До любых потенциально разрушительных преобразований предусмотреть экспорт/резервную копию и отказ без изменения исходных данных.
8. Не использовать реальную пользовательскую базу как тестовый полигон. Для тестов создавать отдельные IndexedDB database names.

## Проверки текущего этапа

- Upgrade заполненной базы v7 -> v8 с сохранением anime и пользовательского прогресса.
- Существующий тест миграции v1 -> последняя версия.
- Полный набор тестов, typecheck, проверка сервера и расширения, production build.
- Ручная проверка в отдельной тестовой базе: отключить интернет, открыть локальную библиотеку, изменить запись, перезагрузить страницу, восстановить соединение и вручную выполнить синхронизацию на тестовом аккаунте/данных.

## Известные ограничения

- `navigator.onLine` является подсказкой браузера о сетевом соединении, а не гарантией доступности конкретного сервиса.
- Внешние изображения, каталоги и API могут не работать без интернета.
- Офлайн-доступ предполагает, что локальный Node/Vite сервер приложения продолжает работать. Отключение самого компьютера или остановка локального сервера не покрывается этим этапом.
- Автоматический reconnect-sync намеренно не включён, чтобы не отправлять изменения или удаления без явного действия пользователя.
