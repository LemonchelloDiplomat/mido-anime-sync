# Надёжная локальная библиотека

**Приоритет:** P1 / основной фундамент проекта  
**Рабочая ветка:** `feature/pr-36-reliable-local-library`

## Цель

Локальная библиотека должна быть надёжным источником данных. Импорт, синхронизация, объединение дублей, очистка и восстановление не должны незаметно терять пользовательские записи, прогресс, оценки, избранное, связи с провайдерами или историю незавершённых операций.

Этот документ фиксирует текущую базу и план аудита/доработки. Наличие функции в коде не считается доказательством её полной надёжности, пока не проверены ошибки, миграции и сквозные сценарии на копии пользовательской базы.

## Уже реализовано в main

- IndexedDB-репозиторий с отдельными хранилищами аниме, агрегированных записей, source entries, разрешений конфликтов и связей между тайтлами.
- Миграции IndexedDB до версии 7, включая хранилища журнала операций, сессий и намерений удаления.
- Атомарные транзакции для ряда связанных изменений библиотеки.
- Раздельное хранение исходных записей провайдеров и построение агрегированной локальной записи.
- MAL и AniList: импорт и двусторонняя синхронизация; Shikimori: импорт и операции обновления/удаления.
- Provider baselines, планирование синхронизации, разрешение конфликтов и защита от части опасных удалений.
- Проверки, не позволяющие продвигать baseline после неудачного локального сохранения или неразрешённого конфликта.
- Журнал операций и сессий синхронизации, сохранение плана до выполнения записей и восстановление незавершённых операций по фактическому состоянию провайдера.
- Snapshot validation, экспорт/импорт и атомарный restore; при восстановлении незавершённые операции и затронутые сессии обезвреживаются, история операций/сессий сохраняется.
- Поиск потенциальных дублей по точным общим внешним ID; совпадения только по названиям намеренно не считаются достаточным доказательством.
- Слияние части связанных сущностей: внешних ID, названий, source entries, агрегированных записей, конфликтных решений и отношений между тайтлами.

## Что осталось сделать

### 1. Полный аудит жизненного цикла данных

- Проследить create/update/import/merge/delete/export/restore для каждой сущности.
- Проверить все IndexedDB-миграции на последовательных версиях старой базы, включая реальную базу с большим количеством записей.
- Проверить целостность ссылок между anime, entries, sourceEntries, conflictResolutions, animeRelations, syncOperations, syncSessions и deletionIntents.
- Проверить поведение при закрытии вкладки, перезапуске браузера, нехватке места, ошибке транзакции и частичном отказе провайдера.
- Проверить, что snapshot содержит все данные, которые должны переживать экспорт/импорт, и что исключённые данные исключаются намеренно.

### 2. Безопасное объединение существующих дублей

- Подтверждать тождество только достаточными идентификаторами; неоднозначные совпадения оставлять раздельными.
- Перед объединением проверять конфликты внешних ID и конфликтующие связи источников.
- Сохранять/согласованно объединять все пользовательские поля и метаданные: статусы, прогресс, оценки, избранное, даты, комментарии, теги и дополнительные поля, если они есть в модели.
- Переназначать все ссылки с исходного ID на канонический ID.
- Не терять provider source entries, baselines, конфликтные решения, deletion intents и ссылки из журнала/сессий операций.
- Обеспечить идемпотентность: повторное выполнение reconciliation не меняет уже согласованные данные.
- Для конфликтующих значений применять документированную политику или требовать явного решения, а не выбирать произвольное значение.

### 3. Журнал операций и восстановление

- Проверить каждый промежуточный момент сбоя для направлений local→remote и remote→local.
- Убедиться, что операция не становится succeeded до подтверждения целевого состояния.
- Проверить, что baseline продвигается только после полного успешного локального сохранения.
- Проверить восстановление после ситуации «удалённый сервис принял запись, но локальная запись не сохранилась» и обратного порядка.
- Проверить, что merge/restore не оставляет операции с потерянными или устаревшими ссылками.
- Сохранять достаточные данные для диагностики и безопасного повторного запуска без повторного применения уже завершённых действий.

### 4. Резервное копирование и восстановление

- Проверить экспорт полного snapshot, включая все обязательные сущности и связи.
- Проверить импорт на пустую и непустую библиотеку, некорректные и несовместимые версии snapshot.
- Гарантировать принцип «всё или ничего»: ошибка проверки/транзакции не должна оставлять частично восстановленную библиотеку.
- Проверить, что restore не смешивает старые provider baselines и новые данные snapshot.
- Проверить корректное состояние журнала и сессий после восстановления.
- Провести практическое восстановление на копии большой пользовательской библиотеки.

### 5. Регрессионное покрытие

- Большая библиотека и несколько источников на один тайтл.
- Дубли с одинаковым MAL ID, AniList ID или Shikimori ID; конфликтующие ID; частичные и неоднозначные совпадения.
- Разные статусы, прогресс, оценки и даты в дублях.
- Повторный импорт, повторное объединение и повторное восстановление.
- Сбои на каждом шаге локальной и удалённой синхронизации.
- Повреждённые snapshot, несовместимые версии и ошибки транзакций.
- Проверка сохранности MAL, AniList, Shikimori и существующей локальной библиотеки после каждого изменения.

## Критерии готовности

- Ни один тестовый сценарий merge не теряет данные, внешние ID или связи.
- Неоднозначные дубли не объединяются автоматически.
- Повторные импорт, merge и restore идемпотентны.
- Сбой синхронизации не создаёт ложный успех и не продвигает baseline преждевременно.
- Восстановление snapshot атомарно и проверено на копии большой пользовательской базы.
- Миграции проверены с предыдущих версий IndexedDB.
- Проходят `npm test`, `npm run typecheck`, `npm run check:server`, `npm run check:extension` и `npm run build`.
- MAL, AniList, Shikimori и текущая локальная библиотека проходят регрессионные сценарии.

## Ограничения PR

- Сначала аудит текущей реализации, затем минимальные целевые исправления.
- Не переписывать интеграции без доказанной необходимости.
- Не менять интерфейс ради косметики; приоритет — целостность данных.
- Не удалять и не перезаписывать пользовательские записи ради автоматического устранения дублей.
- Проверять миграции и восстановление на копии данных, оригинальную библиотеку не использовать как тестовый полигон.
